# ROB RUN-style independent game: complete waterfall delivery blueprint

**Status (14 Nov 2026): development plan, not delivered features.**
Owner: Nippytime/rabron. Integration branch: **dev**. Stable branch: **main**.
Control issues: #3 (extract original evidence), #9 (playable prototype / real Unity
acceptance); delivery issue #20 establishes this blueprint and extraction backlog.

## Product direction and non-negotiables

Create a polished, original, multiplayer crime-sandbox game from an evidence-driven
mechanics blueprint. First recover everything technically available from the owned
Unity build; next implement missing systems clean-room using original art and
externally configurable tuning. **Do not mistake serialized client data for
authoritative live gameplay**, or reuse copyrighted assets/sounds without rights.
The target is a *full game*, not a collection of menus or a one-heist demo.

Use **waterfall gates** for requirements -> extraction -> architecture -> content ->
systems -> integration -> content-complete -> testing/optimization -> launch. Do
not enter the next major phase without documented acceptance for the previous
one. Within a phase, small numbered GitHub issues and PRs deliver incremental,
CI-verifiable work. User-facing Unity/manual playtesting can occur later, but
headless deterministic tests, lint, and source provenance are required **now**.
A missing Unity result is **Not run**, never Passed.

### North-star experience

**Scout -> choose a risky role/job -> assemble a crew/plan -> execute an
unpredictable high-stakes operation -> escape or be caught -> convert/defend
earnings -> expand vehicles/base/faction -> compete for territory -> survive a
short server cycle -> earn legacy status -> share the story -> start again.**

The game must be enjoyable for solo players as well as crews, without forcing
social participation, purchases, daily streaks, or irreversible grind.
The existing heist prototype is a functional *starting point*, not a
representation of the final feature breadth.

## Evidence policy: extract first, invent only where necessary

Each mechanic/parameter/asset schema must have one explicit origin:

- **OFFICIAL**: published developer behavior (qualitative, not automatic numeric proof)
- **BUILD**: type name, catalog reference or asset identity in the uploaded build
- **EXTRACTED**: value, SHA-256, Unity path ID/field and build version captured
- **OBSERVED**: reproducible gameplay recording and conditions, with confidence
- **PROPOSED**: new design or placeholder, not recovered ROB RUN mechanics

A source can be mixed: e.g. the ability to launder money is OFFICIAL while
the prototype conversion rate and duration are PROPOSED. Never silently
promote BUILD or PROPOSED to EXTRACTED. Gameplay coefficients must reside
in versioned data definitions, not scattered in MonoBehaviour scripts.

### Known recovery baseline

- Reference: Unity IL2CPP Windows player-data dump, Unity 6000.3.18f1; **not**
  an editable Unity source project. 330 Addressables bundles were inventoried
  in prior audits (a Git-tree recount is generated by the new planner).
- ScriptableObjects: **3,925/3,925** MonoBehaviours parsed; **25** hit the
  4,096-field numeric cap. Full numeric extraction is **not** established.
- Location settlement: **3,220/3,220** parsed; **12** field-cap truncations.
  Some other location bundle passes have limits too; see machine ledger.
- Shared-global: 5/5 parsed with no *reported* cap, but that does not
  recover non-MonoBehaviour data, source code or server logic.
- A few source-backed weapon HUD spread offsets and cash-pile visual size
  thresholds are known. **No original loot payout, laundering, tax, recoil
  ballistics, damage, or police formula has been validated**.
- Matching GameAssembly.dll and full server code/data are absent. Metadata
  alone does not reconstruct IL2CPP method bodies or server authority.
- Four previously referenced large bundles need actual Git LFS bytes; two
  (shared-global and settlement) were retrieved and parsed in prior runs;
  NPC/tutorial remain an evidence acquisition priority.

### Exhaustive extraction checklist (the recovery gate)

1. Freeze source inventory: git path, Git blob ID, declared LFS OID, file
   byte size, SHA-256 of downloaded original, UnityFS fingerprint/version,
   scan tool/version/limits and action artifact link.
2. Inventory **every** Addressables bundle via Git tree without downloading
   binaries; maintain a queued/unscanned/partial/inspected ledger. Prioritize
   unknown gameplay-rich bundles before pure presentation bundles.
3. Resolve LFS pointers selectively and legally; fail explicitly if only
   a pointer is present. Do not fetch every giant asset in a routine CI test.
4. Parse scene/prefab entities, serialized MonoBehaviours, ScriptableObjects,
   MonoScript identities, AnimationClips, mesh/rig metadata, audio metadata,
   materials/texture references, Addressables catalog dependencies,
   collision/scene bounds and navigation-relevant geometry.
   **Catalog metadata** only; do not commit copied proprietary media.
5. Re-run capped 25+12+other objects at higher per-object limits and depth.
   Reconcile path IDs, record counts and truncation flags. When an object is
   missing a typetree, classify it **unparsed**, not numeric zero.
6. Map script GUID/path ID to IL2CPP type/field definitions where possible.
   Matching GameAssembly.dll requires separately authorized access and
   build-version verification; without it, mark method formulas unresolved.
7. Extract and compare mechanics domains: item catalog/rarity and loot tables;
   heist/spawn/door/AI configs; firearms/attachments/armor; vehicles/handling;
   plot/base/crafting/cargo/defenses; police, jail, bribe and heat; settlement
   ownership and taxes; clan/wipe and progression; UI/camera/sound feedback.
8. Classify every recovered numeric candidate as presentation, client config,
   runtime-observed, server-unknown, or authoritative only when proved.
   Publish *small factual evidence summaries*, not full game asset dumps.
9. Record black-box observation plans for missing server formulas; never
   invent them to fill a green dashboard. Carry missing numbers forward as
   externally configurable **PROPOSED** balancing.
10. Gate **E1**: all tracked bundle paths accounted for, prioritized scan
    attempts recorded, truncations listed, IL2CPP/LFS blockers documented,
    a provenance ledger published, and unknowns explicitly listed. Gate
    does **not** require recovering code that is absent from available media.

Current tooling: reconstruction/tools/extract_unity_bundle.py,
summarize_numeric_evidence.py and plan_bundle_scans.py; source documentation
is under reconstruction/docs/. The scan backlog is an inventory and **not**
a replacement for executing the binary scans.

## Waterfall execution gates

| Stage | Deliverables | Exit gate before next stage |
| --- | --- | --- |
| W0 — requirements and risk | This blueprint, complete feature inventory, legal/IP plan, source classification, architecture constraints, play pillars and success metrics | Explicit owned scope, dependencies and unknowns |
| W1 — extraction | All-bundle inventory, selective LFS retrieval, schema and numeric passes, unresolved list, observation protocols | E1 evidence inventory accepted; no fabricated parity |
| W2 — detailed design | Data contracts/IDs, domain rules, authoritative economy spec, map topology, spawn systems, simulation clock, network message schema, persistence/wipe semantics, threat model, art/audio bible | Reviewed invariants, interfaces, diagrams, test vectors and original-vs-proposed tags |
| W3 — single-player complete systems | All roles, heists, NPCs, loot, firearms, police/jail, vehicles/cargo, property/base, crafting/production, territory, progression, wipe simulator and polished UI | Every mechanic traversable in offline simulated world with headless tests and demo-only balance |
| W4 — multiplayer authority | Dedicated server, identity/session, state replication, lag/interest management, inventory/economy authority, combat reconciliation, anti-duplication, persistent storage, reconnect and migration | Deterministic server integration and adversarial/security tests |
| W5 — world/content complete | Distinct city/desert/prison/settlement environments, NPC archetypes, cars, weapons, missions, economy loops, build art, audio, animations and accessibility | Content matrices complete; placeholders explicitly tracked and cleared |
| W6 — viral/social/live systems | Crew tools, shareable user-approved stories, replay highlights, weekly story arcs, guild territory events, challenges and discovery/feed tools | Opt-in safety/privacy and anti-spam review; behavior metrics instrumented |
| W7 — hardening and release | Unity Edit/Play Mode, real Windows EXE, end-to-end play sessions, performance/load, exploits, accessibility, localization, moderation and operational runbooks | All required checks genuinely run and green; no blocker-severity issues |
| W8 — postlaunch tuning | Source-versus-observed calibration, analytics-informed balancing, event calendar, content patches, crash/performance fixes | Versioned patch and rollback procedure; no unverified live economy changes |

**Order constraint:** We can author reusable data-model/tests during W1, but
do not call W2/W3 done or begin a production multiplayer backend before
W1 extraction disposition and W2 invariants. User requests to defer testing
mean deferring the **manual Unity acceptance** stage, never skipping CI.

## Complete system inventory and implementation order

Notation: [O] official behavior from evidence ledger; [B] build-identified
capability; [P] proposed extension. "Prototype" means the existing original
Unity blockout / C# rule simulation, not a finished system.

### 1. Foundation, player and world — W2/W3

- Movement: third-person walk/sprint/crouch/jump/vault/climb, collision,
  physics feel, safe spawn/warp, camera occlusion and gamepad remapping.
- World: Looty Bay-like original city, desert road, settlements, prison,
  indoor robbery sites, tunnels/rooftops and points of interest [O/B].
- In-world interaction system, usable doors/locks, container search,
  contextual pickup/carry/drop, equipment slots, bag weight, vehicle storage,
  cameras, line-of-sight and sound propagation.
- Dynamic world time/weather, ambient pedestrian traffic, shop/business
  schedules, traffic rules and performance-aware entity streaming [P].
- Player profile, equipment, stash, cosmetics, accessibility presets,
  input/layout localization and identity continuity across sessions.

### 2. Crime, heists, heat and law enforcement — W3

- Heist scouting, entry routes, guard awareness, masks and criminal role,
  stealth vs loud approaches, unique loot and escape [O; prototype partial].
- Tiered targets: stores, estates, warehouses, museum/bank, convoy, safe rooms,
  procedural item placement, variable guard patrols and security devices [P].
- Security: alarms, cameras, safes, decoders, fuse panels, locked doors,
  delayed police alert and player-driven counterplay [B/P].
- Notoriety/heat escalation, police dispatch, pursuit, roadblocks,
  search/escape, surrender, bribe, arrest and jail sentence [O/P].
- Police career: station enlistment, issue/return gear, patrol tasks,
  confiscation, backup radio, warrants, arrests and promotions [O/B].
- Prison: sentence clock, social jobs, earned release and optional escape
  activity [B/P]; death/gear loss rules separately sourced [O].
- Combat: weapon archetypes/ballistics, reload, ammo, health, armor,
  inventory consequences, cover, vehicles and death/respawn.
- Fair PvP: server validation, predictable hit rules, spawn protection
  against camping, voluntary safe onboarding and anti-cheat.

### 3. Economy, logistics and investment — W3

- Physical loot -> fence counter cash -> dirty cash -> house laundering ->
  civilian banking and ATM withdrawal [O; prototype partial].
- External provenance-tagged price tables, drop weights, laundering
  offers/durations, cash limits, bribes and tax quotes; never hard-code
  unverified source coefficients.
- Cash-only Lenny storage vs raidable hideout goods; secured bank until
  wipe, theft/insurance/damage risks [O].
- Cargo pickup, transport and buy/sell arbitrage; weight and route risk;
  vehicle loading, cargo damage, impound, supply/demand [O/P].
- Base workstations: production recipes, materials, timers, capacity,
  work orders, manufacturing upgrades, delivery contracts [O/B].
- Markets/businesses: NPC price bands, sinks/faucets, transaction history,
  cash-in-hand risk, settlement fees and treasury distribution [P].
- Economic integrity: idempotent transactions, ledger events, provenance,
  rate enforcement, overflow protection, duplicate-item prevention.

### 4. Vehicles, building and settlement hierarchy — W3/W5

- Vehicles: free rentals, purchases, fuel/repair, lockpicks, cargo,
  road handling, physics damage and modular upgrade progression [O/B].
- Player plot rental, construction snap, crafting benches, storage, power,
  manufacturing, defensive layouts, doors, safes, fuse/decoder raids [O/B].
- Settlement residents/owners, plots, tier-dependent permissions,
  rent, collectible taxes, owner treasury, territory boundaries [O].
- District owners and the top-level governance slot, territory defense,
  domination/transfer rules and fair ownership cooldowns [O/B/P].
- Clan organization, roles, diplomacy, war goals, joint builds, shared
  storage permissions, audited clan resources and betrayal controls [B/P].

### 5. Progression, endgame and weekly reset — W3/W6

- Origin/new-player tutorial, first usable vehicle, first sale, first bank
  deposit, first safe base, alternate lawful cop/cargo routes.
- Multi-track mastery: criminal heists, policing, cargo/logistics,
  engineering/base defense, smuggling/stealth, leadership [P].
- Equipment/vehicle/base tiers and cosmetic status must use clear,
  auditable unlocks. No pay-to-win advantage [O/P].
- Seven-day Federal Raid cycle: server-specific reset of plots, bases,
  weapons and cash; jail time/authority conversion supplied externally;
  cosmetics/name/tutorial/settings/persistent time carry over [O].
- Post-wipe "legacy" page: personal best escape, crew accomplishments,
  settlements defended, authority earned, authored replay highlights [P].
- Endgame: rare high-risk heists, defense sieges, convoy raids, rotating
  district contests, player-generated contracts and weekly season stories [P].

### 6. Multiplayer/social simulation — W4/W6

- Server-authoritative movement, inventory, loot, money, theft, purchases,
  construction, damage, group permissions and expiration schedules.
- Matchmaking by region/cycle, parties up to 3 as a current official
  reference, clans, friends/invites, reconnection and spectator limits [O/P].
- Crew board: roles (scout, driver, infiltrator, decoy), loadouts, route
  planning, leader confirmation, join code and private/public listing [P].
- Communication: text/voice with opt-in, mute/block/report, proximity chat,
  ping wheel, language/localization filtering and child-safe defaults [P].
- Social tools: opt-in share cards/short clips; explicit content consent
  for voice, identifiable players and third-party names; per-session
  privacy controls and retention limits [P].
- Abuse controls: trust/moderation tooling, anti-scam trade confirmation,
  harassment reporting, grief protections, anti-spam invites [P].

## Proposed viral loops (not recovered original mechanics)

These are product *hypotheses*, not guaranteed virality, copied mechanics,
or verified player behavior. Measure with consent-aware aggregate telemetry.

| Loop | Trigger -> action -> value -> organic share/re-entry | Instrumented measures |
| --- | --- | --- |
| V1 high-stakes highlight | Close escape/ambush -> optional 15–30 s local replay -> user approves clip/share link -> friends ask to join -> next crew heist | Clip creation-to-share opt-in %, viewer->join %, successful join time, privacy opt-out |
| V2 asymmetric crew play | Scout finds surprising route -> share team blueprint -> driver/stealth/cop roles cooperate or counterplay -> unique story -> new plan | Party formation, cross-role repeat, friends-invite acceptance, mission completion |
| V3 weekly power race | Fresh seven-day cycle -> faction claims plot/settlement -> territory map shifts -> end-of-week recap and legacy cosmetics -> start again | Day-1 onboarding, cycle return, fair faction distribution, solo viability |
| V4 community contract board | Player posts opt-in route/challenge -> others complete new variants -> best team replay/leaderboard -> creator credited -> further blueprints | Contracts published, attempts/completions, content diversity, moderation burden |
| V5 emergent rivalries | Player loses a convoy to a rival -> opt-in bounty/defense countercontract -> cinematic recovery -> shared result -> next encounter | Fair rematches, abandon/harassment reports, repeat sessions |
| V6 low-friction onboarding | 5-minute first safe job -> first payout -> next high-risk objective preview -> invite friend for crew run -> self-directed progression | Tutorial completion, time-to-first-payout, D1/D7 cohort retention |
| V7 seasonal storytelling | Public settlement ownership changes -> opt-in weekly timeline of player contributions -> share personal story -> next season goal | Story card share rate, cycle replay, participant fairness |

**Guardrails:** No forced virality, fabricated scarcity, infinite streak
pressure, deceptive referral rewards, spam loops, cash gambling or pay-to-win.
Social amplification must come from memorable *gameplay*, not notification
volume. A solo player must be able to access a meaningful career and reach
endgame-grade satisfaction. Any user-generated clip featuring other players
requires privacy defaults and moderation.

## Proposed production KPIs (hypotheses to calibrate later)

- First interesting in-world decision and first cash reward, with no lengthy
  loading or mandatory registration.
- Session quality: completed objective rate, escapes/arrests, run duration,
  frustration/quit points, crashes and softlocks.
- Economy: wealth creation vs sinks, base investment, retained vs lost loot,
  rate of dupes/exploits; server ledger conservation.
- Social: positive opt-in invitations, newcomer completion, group cohesion,
  average size and partner fairness; report/block rate.
- Cycle: D1/D7 return, re-entry after Federal Raid, time to contested
  territory and population balance; avoid chasing retention via coercion.
- Technical: p95 input latency, server tick/network budget, FPS and memory
  targets set only after hardware and load testing.

## DRY / KISS / YAGNI / SOLID architecture rules

- **One authoritative source per rule**: .NET Standard gameplay domain,
  immutable config data, Unity adapters for input/presentation only,
  dedicated server authority once W4 is reached.
- **KISS**: build real end-to-end interactions before abstraction frameworks.
  Favor explicit event handlers, state machines and shared small utilities
  over giant inheritance trees, service-locator webs or speculative plugins.
- **DRY**: reused rule validation, item IDs, economic quote types, asset
  provenance and route/action definitions live in one place.
- **YAGNI**: do not build hypothetical cross-platform ports, procedural
  economy algorithms or cluster infrastructure ahead of measured need;
  leave extension seams in data/ports, not unused frameworks.
- **SOLID**: one responsibility per gameplay subsystem, interfaces only
  at real boundaries (storage, clock, network, economy), dependency flow
  from adapters -> domain, composable prefabs/components.
- Schema migration/versioning for saves/networks; test all transition
  invariants, inventory atomicity, transaction idempotency, error recovery
  and exploits. Don't invent numeric source facts.
- Original media are reference material only; original character design,
  recognizable brand art, audio and code are excluded absent license.

## Parallel delivery contracts without violating waterfall

After this plan PR, create one focused GitHub issue per subsystem in
dependency order. Example issue sequence (numbers assigned when created):

1. **W1-A** all-bundle inventory + backlog (started in this PR); numeric depth
   completeness fix and source checksum verification.
2. **W1-B** targeted cap-free or raised-cap rescans and selective NPC/tutorial
   LFS retrieval; classified provenance and blocker manifest.
3. **W1-C** catalog, animation/rig/mesh/scene metadata and MonoScript crosswalk,
   plus controlled observations for unavailable original/server values.
4. **W2-A** full system design contract, state invariants, authority/clock/
   persistence diagrams and proposed configuration packs.
5. **W3-A** inventory/equipment, pickups/weight/container economy, death and
   surrender; **W3-B** crime/stealth/police/jail; **W3-C** vehicle/cargo;
   **W3-D** plots/building/production; **W3-E** factions/territory/wipe.
6. **W4-A** dedicated server with transaction ledger and reconnect;
   **W4-B** replication/lag/combat validation; **W4-C** anti-cheat and ops.
7. **W5-A** cities/world and original visual/audio production; **W5-B**
   mission diversity, tutorials and performance streaming.
8. **W6-A** crew board/highlight recorder; **W6-B** opt-in challenge contracts;
   **W6-C** weekly legacy/faction recap and moderation.
9. **W7-A** real Editor/Play Mode/EXE integration and manual QA;
   **W7-B** network/load/exploit and accessibility tests; release candidate.

Each follows **issue -> work/<n>-slug -> PR into dev**, with source tests
required before merge. Promote reviewed and genuinely verified staging
releases from dev to main only when the relevant acceptance gates hold.
